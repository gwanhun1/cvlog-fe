## 변경

- BE `GET /posts/public/sitemap`: 공개·미삭제 글의 ID, 제목, 공개 상태, 생성·수정일만 단일 쿼리로 조회. 본문·사용자·태그 JOIN 없음. 50,000개 초과 시 조용히 잘라내지 않고 실패.
- FE `/sitemap.xml`: 요청마다 XML을 만드는 Pages SSR에서 XML 전용 App Route의 ISR로 변경. 화면 페이지는 기존 Pages Router 유지. 300초 간격 갱신, 실패 시 이전 정상 XML 유지. 최초 빌드가 실패하면 불완전한 sitemap으로 배포하지 않음.
- sitemap 조회는 전체 8초 제한 및 취소 신호를 사용하고, 오류를 빈 성공 결과로 바꾸지 않음. 실제 수정일을 사용하고 고정 페이지에 요청 시각을 `lastmod`로 넣지 않음.
- 본문: 404는 실제 404, 403은 소유자 클라이언트 조회를 위한 비공개 화면. 일시 장애·잘못된 응답은 throw하여 ISR 정상 HTML을 유지. 캐시 없는 요청의 장애는 500.
- 공개 목록도 조회 실패를 빈 목록으로 캐시하지 않음.
- `/article/page/2`부터 서버 렌더링되는 이전 글 페이지와 실제 이전/다음 링크 추가. 각 페이지 자기 canonical, `/article/page/1`은 `/article`로 리디렉션. 공개 최신순은 페이지 이동, 검색·인기순·내 글은 기존 추가 로딩 방식 유지.

## 검증 명령

최종 결과: FE 단위 테스트 10개, BE 테스트 24개 통과. 양쪽 빌드·타입 검사 통과. 최종 ISR 테스트에서 실제 300초 만료 후 sitemap·목록·본문의 장애 중 정상 캐시 유지, 복구 후 새 내용 갱신을 확인했다. 캐시 없는 본문은 장애 시 500, 없는 글은 404, 비공개 글은 본문 없는 noindex 응답으로 검증했다.

Chrome의 로컬 프로덕션 빌드에서 이전/다음 페이지, 페이지별 canonical, 인기순 데이터 로딩, 최신순 복귀, 2페이지에서 검색 시 `/article?q=...`로 이동하는 흐름도 확인했다. 테스트용 API의 CORS 응답을 앱 요청 헤더와 맞춰 검증했으며 운영 CORS 설정은 변경하지 않았다.

FE:

```sh
node --test scripts/test-seo.cjs
npx tsc --noEmit
node scripts/test-seo-isr.cjs
```

ISR 테스트는 별도 임시 복사본과 가짜 API를 사용해 프로덕션 빌드를 실행한다. 실제 300초 TTL 이후 API 503을 재현하고 sitemap·목록·본문 유지 및 복구 후 갱신을 확인한다. 운영 데이터나 설정을 바꾸지 않는다.

BE:

```sh
npx jest src/posts/posts.controller.spec.ts src/posts/posts.service.spec.ts src/posts/sitemap.repository.spec.ts --runInBand
npm run build
```

BE 기존 ESLint 설정은 설치되지 않은 `react-app` config를 참조하여 실행 단계에서 실패한다. FE의 기존 `viewCount` effect 의존성 등 경고는 남아 있다.

## 운영 반영 순서

1. 백엔드 먼저 배포하고 `/posts/public/sitemap`의 200 응답, 공개 글 수, 응답 시간을 확인한다. DB 마이그레이션은 없다.
2. 프론트엔드 빌드·배포. sitemap 빌드에서 새 백엔드 API를 읽으므로 순서를 바꾸면 안 된다.
3. 공개 `/sitemap.xml`, `/article`, `/article/page/2`, 71·72·75·80번 본문의 HTTP 상태·canonical·본문을 확인한다. sitemap에 최신 공개 글이 포함돼야 한다.
4. 주요 미색인 글의 Google 실제 URL 테스트 후 색인 요청. 이후 크롤링 날짜·색인 상태를 추적한다. 요청은 색인을 보장하지 않는다.

이 작업에서 운영 배포·설정 변경·색인 요청은 수행하지 않았다. 지난주 연결 실패 전체 원인은 여전히 미확정이다.
